## How the game works

- `ProjectSettings/EditorBuildSettings.asset` enables `Assets/menu.unity` at index 0 and `Assets/Main.unity` at index 1.
- `UI/ButtonManager.cs` asynchronously loads the selected scene and updates a loading slider. `UI/LoadingScreenManager.cs` implements a separate loading-scene approach; its expected scene index 2 is absent, so its static entry point falls back to direct loading. Consolidate only after establishing which path is used.
- `Controls/GameInput.cs` creates one Input System action map in code. Keyboard, mouse and some gamepad controls are supported. Inventory slots have keyboard/numpad bindings; they have no gamepad bindings.
- `UI/UIInputModuleBootstrap.cs` replaces legacy UI input modules at runtime. It does not by itself repair missing serialized UI scripts.
- `Characters/Character.cs` owns movement, jumping, Sleep, Intelligence, shooting and door interaction. Horizontal speed is base speed plus nonnegative Sleep. A normal lab shot costs one Sleep. Losing either stat below 1 ends the run.
- `World/Teleport.cs` tracks nearby colliders, starts a delayed transfer, and uses `TeleportController.cs` to animate its entrance and exit doors.
- `Inventory/LootBoxItem.cs` handles E-based pickup. `InventoryController.cs` provides nine slots, stacks items by concrete script type, hides the retained pickup object, and displays its icon/count. A refused pickup stays in the world.
- Books add Intelligence; shaverma adds Sleep; energy drinks add Sleep and permanently increase base speed. A collected lab uses `Character.ThrowLab()` and costs ammunition rather than Sleep.
- `Characters/Prepod.cs` periodically shoots grade projectiles and needs 5 through 14 lab hits, selected randomly at startup. Player labs and enemy grades each apply damage once per projectile using a hit guard.
- `World/GameSession.cs` accepts the first win/loss result, writes the result label, and creates restart/menu controls. Single-scene loading resets the result. Character and inventory input stop after a result, but other simulation is not globally paused.
- `Cameras/CameraController.cs` follows the player with smoothing and optional bounds. Audio triggers and a fake Windows-error overlay provide atmosphere. Video scripts support VideoPlayer; the existing Main scene also has a built-in VideoPlayer.
- The timer/provider system is separate from the door countdown. Its fade callback is declared but never called by Timer.Update(). Test.cs and DoorOpenTrigger.cs are empty placeholders, not tests.

## Findings from the code

These are source-review findings; scene-specific reproduction remains required.

| Priority | Evidence | Implication / proposed direction |
| --- | --- | --- |
| High | Character.Update uses ActionHeld; Teleport.Activate resets curentWTime every call. | Holding E postpones teleport completion until calls stop. Start a single interaction with an explicit in-progress guard. |
| High | Teleport trigger enter/exit toggles playerInTarget for every collider. | A projectile or other object can change door eligibility. Track the actual player's overlapping colliders. |
| High | Character.CheckGround uses OverlapCircleAll and colliders.Length > 1, without a ground mask. | Nearby triggers can count as ground; self-collider assumptions are fragile. Use explicit ground filtering and a nonallocating query where appropriate. |
| Medium | Character.Run moves transform.position in Update while jumping uses Rigidbody2D. | Horizontal movement bypasses the normal physics movement path. Verify wall/step behavior and use one consistent physics-based movement implementation. |
| Medium | Character.Action searches all teleport tags each frame while E is held; status/audio getters perform additional lookups. | Repeated searches, allocations and side effects scale with frame rate. Keep references to the nearby interaction and make status reads side-effect-free. |
| Medium | Character.Awake resets serialized Sleep to 10; Prepod.Awake overwrites serialized needLabs randomly. | Inspector tuning is misleading. Make starting stats and difficulty/randomness explicit, with reproducible values for testing. |
| Medium | Prepod.Shoot and door countdowns have no GameSession.IsOver guard. | World activity can continue after the result despite locked player controls. Decide and implement consistent end-of-run behavior. |

## Runtime evidence and limits

- Main was opened in Unity 6000.3.27f1 and entered Play Mode successfully on 2026-11-21. The Console showed zero errors during the observed startup and short test.
- Mouse firing spawned BulletLab clones and decreased displayed Sleep from 10 to 9 and then 8. Space input produced a visible airborne player pose and camera response. Extended movement/collision behavior was not verified.
- Enemy BulletOcenka clones were observed. Enemy damage, victory, loss, restart, menu interaction, doors and inventory have not been fully exercised.
- Unity logged H.264 timestamp and color-primary warnings for usb_soft.mp4. A later Console observation also showed a color-primary warning for logo_video.mp4. These warnings do not establish a gameplay failure.
- Testing was paused when the user redirected the task to reading first. The last observation still showed Unity in Play Mode. No further gameplay input was sent after that redirection.
- Unity MCP tools were not exposed to this chat; UI inspection used the computer-use skill. No MCP connection settings were changed.

## Verification learnings / error history

- The exployt message, learning and ID tools were not available in this chat. Notes/TODOs are stored here; registry IDs were generated locally as ten hexadecimal characters.
- Headless Unity inside the sandbox stalled at licensing. Do not treat that as a game compile failure or start a second editor against an already open project.
- `dotnet build StudentSurvival.sln --no-restore` failed before compilation with MSB5004: duplicate StudentSurvival.Characters project names in Unity's generated solution. This does not demonstrate a Unity compiler failure. Use the Unity compiler/build pipeline and regenerate IDE files if needed.
- The first sandboxed .NET attempt failed at registry access before compilation. The unsandboxed retry exposed the generated-solution issue above.
- Read and map the project first, then test against a checklist. A successful startup and a few working inputs are insufficient evidence for a full-game pass.
